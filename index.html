Role: primary backend Status: pre-launch Shape: modular monolith

System architecture

One NestJS API serves two clients. The CMS never writes curriculum tables directly—it calls signed /cms/v1/* endpoints. Mobile consumes Clerk-authenticated /users/me/* routes. Business rules live in the API; clients share Zod schemas and types.

Performance & caching

Mobile cold load reduced from ~4–5 API calls to ~2 via aggregated GET /users/me/learn and Redis cache-aside. Canonical task payloads cached; option shuffle applied after cache hit — never stored shuffled in Redis.

Stripe webhook idempotency

Flow validated in Stripe test mode — no live production revenue claimed.

  1. 1 Mobile calls POST /users/me/subscription/checkout → Stripe Checkout session URL
  2. 2 Stripe sends event → verify signature on raw body (not parsed JSON)
  3. 3 Check event.id not already in stripe_webhook_events — skip if duplicate
  4. 4 Upsert user_subscriptions inside transaction — idempotent on replay
  5. 5 Invalidate subscription cache prefix · record event ID before processing completes

Engineering decisions

Modular monolith
Simpler transactions and deployment; clear module boundaries for future extraction.
Aggregated REST endpoint
Known mobile data shape; faster to ship and cache than GraphQL.
Explicit cache-aside
Typed keys and invalidation beside writes—not hidden framework magic.
