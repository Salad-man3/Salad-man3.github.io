Case study

Ghaya Go / Tayf

Primary backend · Pre-launch · Modular monolith

System context

One NestJS API serves two clients. The CMS never writes curriculum tables directly—it calls signed /cms/v1/* endpoints. Mobile consumes Clerk-authenticated /users/me/* routes. Business rules live in the API; clients share Zod schemas and types. The surface is 54+ HTTP routes across six controllers: 22 learner, 28 CMS write, plus public catalog, webhooks, and health.

NestJS modules

Seven modules. UsersModule started as one service and was split into five: curriculum read, gamification, subscription, leaderboard, and session fetch.

UsersModule
Progress, learn window, gamification, subscriptions
CoursesModule
Public paginated course catalog

CRUD, publish, reorder, media presign, audit logs
WebhooksModule
Stripe and Clerk inbound events

Redis cache-aside with typed keys
AuthModule
Clerk JWT guard for learner routes

Liveness and readiness (DB + Redis)

Authentication boundaries

Client Mechanism Protects

Stripe Webhook signing secret + raw body Subscription lifecycle events

Learner routes verify lesson, quiz, and task IDs belong to the user's active course before awarding points.

Backend scope

  • Curriculum CRUD and publish — Course → Module → Lesson/Quiz → Task
  • CMS write API — CRUD, reorder, media presign, audit logging
  • Student progress — aggregated learn-window, sessions, gamification
  • Auth — Clerk JWT on mobile, API key + HMAC on CMS
  • Redis cache-aside — typed keys, TTLs, prefix invalidation
  • Stripe subscriptions — test mode, webhook dedup, idempotent upserts
  • Shared packages — Zod validation, types, typed HTTP client
  • Ops — health probes, GitHub Actions, GHCR Docker images

Write path

Progress updates, CMS publish, and Stripe webhooks follow the same pipeline. Multi-step writes run inside sequelize.transaction().

Performance & caching

Mobile cold load dropped from four or five API calls to about two via GET /users/me/learn and Redis cache-aside.

Canonical task payloads are cached. Option shuffle happens after the cache hit — shuffled order is never stored in Redis.

Key domain TTL Invalidated when
Course structure / task trees 24h CMS publish / unpublish
Published course list 10m Course publish
User progress 30s Any gamification write
Learn snapshot 30s Progress or curriculum change
Leaderboard 45s Time-based refresh
Subscription state 5m Stripe webhook

Stripe webhook idempotency

Validated in Stripe test mode. No live production revenue claimed.

  1. 01 Mobile calls POST /users/me/subscription/checkout → Checkout session URL
  2. 02 Verify the Stripe signature on the raw body, not parsed JSON
  3. 03 Skip if event.id is already in the webhook event ledger
  4. 04 Upsert the subscription mirror inside a transaction
  5. 05 Invalidate the subscription cache prefix

Testing

141 API unit tests, 32 validation-package tests, 22 lesson-logic tests, 9 API e2e tests with Supertest. About 204 backend-focused tests in total, ~65% API statement coverage. Subscription and leaderboard services are thinner on unit tests — open gap. CI runs pnpm build, lint, and test on every PR; migration smoke on push to main. E2E is not a CI gate yet — by design for now.

Engineering decisions

Modular monolith
I kept one deployable because cross-module transactions matter more than service boundaries at this team size. The module split is real — I'd extract later, not now.
Aggregated REST endpoint
GraphQL would have been prettier on paper. Two clients, one backend engineer, known mobile shape — I shipped /users/me/learn and cached it instead.
Explicit cache-aside
I write invalidation beside the write path on purpose. Hidden framework caching is how you get stale learn tabs and no idea why.

Private pre-launch team product. Primary scope: backend and API integration. Stripe validated in test mode; no live production traffic claimed.

What broke

Real bugs from Ghaya — not hypothetical war stories.

  1. 01

    Stripe renewals updated nothing

    Symptom
    Checkout worked; subscription renewals silently failed to update period end.
    Cause
    The handler cast event.data.object once as a Checkout Session and reused that variable for invoice.payment_succeeded.
    Fix
    Branched per event type, mapped fields from Stripe.Invoice, recorded the event id before processing so retries are no-ops.
  2. 02

    Learn tab over-fetching

    Symptom
    Mobile cold load fired four or five parallel API calls before the trail UI could render.
    Cause
    No aggregated endpoint — progress, modules, course progress, and lesson percentage each had their own route.
    Fix
    Built GET /users/me/learn, added read indexes in migration 009, cached the snapshot for 30s. Down to about two calls.
  3. 03

    Points farming via scope bypass

    Symptom
    Any authenticated learner could post progress for any published task, not just their active course.
    Cause
    Lesson, quiz, and task IDs were not verified against the user's active course before awarding points.
    Fix
    Added active-course assertions on curriculum-read and gamification paths.
  4. 04

    Concurrent completions double-awarded points

    Symptom
    Task completion updates points, streak, and quests — concurrent mobile requests could leave inconsistent state.
    Cause
    Multi-step gamification writes were not atomic; duplicate progress rows were possible.
    Fix
    Wrapped writes in transactions, deduped existing rows, added a uniqueness constraint on user + task.
