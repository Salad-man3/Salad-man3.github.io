Ghaya Go, under the hood

One NestJS API serving an Expo mobile app and a Next.js CMS from a Turborepo monorepo. I was the main backend engineer from February to August 2026, and I wrote it from an empty repository.

There is no live traffic, so no number on this page comes from production.

Expo app the API served (not my UI work).

The shape

The CMS never writes curriculum tables directly. It calls signed API endpoints, so every business rule lives in one place and every editorial write lands in an audit log.

Decisions I'd defend

API
One deployable, not services

Cross-module transactions mattered more than service boundaries at this team size.

Why
Module split is real; extract a service later.
Cost
One blast radius if the API process dies.
API
Aggregated endpoint instead of GraphQL

Ship GET /users/me/learn and cache it.

Why
Two clients, one engineer, known screen shape.
Cost
Less flexibility than GraphQL for editors.
Data
Cache invalidation beside the write

Every write clears its own Redis prefix in the same function.

Why
Hidden framework caching is how you get a stale screen.
Cost
More boilerplate on each write path.
Data
Publishing is all or nothing

Publish or delete a course in one transaction.

Why
Half-written content must never go live.
Cost
Longer locks on big courses.

Two bugs I fixed

The learn screen over-fetched on every cold start
Symptom
The mobile app fired four or five requests before it could draw the learn screen.
Cause
Progress, modules, course progress and lesson percentage each had their own route, and the client needed all of them for one screen.
Fix
One GET /users/me/learn endpoint that reads all four, read indexes in migration 009, and a 30-second Redis snapshot. About two calls now.
A race in gamification
Symptom
Completing the same task twice at nearly the same moment could record it twice.
Cause
The check for an existing completion and the insert were separate steps, so two requests could both pass the check.
Fix
Removed the duplicate rows, added a UNIQUE (user_id, task_id) constraint, and moved the writes into a transaction. The database now refuses the second row.
